# 案1: 洪水マップ 超高機能・高性能版

## 1-1. 調査で分かった事実

### 令和8年8月千葉豪雨（2026/8/13–14）
- 死者 **10人**、浸水被害 **約1500棟**、千葉市で車両 **約2500台**が路上に、避難指示は一時 **40万人超**、**21市4町に災害救助法適用**（[NHK](https://news.web.nhk/newsweb/na/nd-20260815de44322) / [全国災害ボランティア支援団体ネットワーク](https://www.saigaivc.com/20260817/)）
- 千葉市中央区の**冠水したアンダーパスから遺体**が発見されている（[千葉日報](https://www.chibanippo.co.jp/articles/1653770)）

### 🔥 最重要ファクト: ハザードマップが機能しなかった
ウェザーニューズが浸水被害報告 **約2万件**（アンケート10,009件＋ウェザーリポート約1万件）を分析した結果（[ウェザーニュース](https://weathernews.jp/news/202608/140171/)）:

> **被害を示すリポートのうち 55.7% が「低位地帯または浸水想定区域"外"」から寄せられた**（区域内は 44.3%）
> = **2人に1人が浸水想定区域の外で被災**
> 「色が付いていない場所だから安全とは限らない」

- 原因は**内水氾濫**。1時間100mm超 ＝ 一般的な下水道の処理能力（約50mm/h）の**約2倍**の雨で排水が追いつかず溢れた。
- 「ペリエ1階浸水」「千葉駅ロータリーもすごい」「JR常磐線のアンダーパスが冠水し通行止め」など、河川氾濫ではない**都市型内水氾濫**の被害報告。

### 🔥 もう一つの空白: 内水ハザードマップがそもそも存在しない
防災白書ベースの整理（[ジチタイムズ](https://www.publicweek.jp/ja-jp/blog/article_60.html) 他）:

| ハザードマップ種別 | 公表済み自治体の割合 |
|---|---|
| 津波・土砂災害 | **95%** |
| 洪水（外水） | **86%** |
| **内水（想定最大規模・下水道区域全域）** | **わずか 7%** |

- 流域治水関連法により下水道（雨水）を実施する市町村に**内水ハザードマップ作成が義務化**されたが、「必要性の認識が低い」「浸水想定区域を示す情報が揃っていない」等で整備が進んでいない。

### 既存ハザードマップの「行動につながらない」問題
国交省の検討会資料などで既に指摘されている（[国交省 ハザードマップのUD検討会](https://www.mlit.go.jp/river/shinngikai_blog/universal_design/pdf/siryou7-1.pdf) / [「わかる・伝わる」ハザードマップのあり方](https://www.mlit.go.jp/river/shinngikai_blog/universal_design/pdf/hazardmap_main.pdf)）:
- 「ハザードマップを見たことがない **31%**」「役に立たない **12%**」
- 浸水深・避難場所の表示だけでは避難行動に結びつかない
- 「自宅が浸水想定区域なのは分かったが、**どのタイミングでどの避難所に逃げればいいか判断できない**」
- 研究側の答えは **「行動指南型ハザードマップ」**（建物の構造・階数で判断基準を変える）だが、まだ研究・試行段階

### アンダーパス冠水
- 国交省データで、**過去20年でアンダーパスの車両水没事故により全国20人以上が死亡**。**夜間・早朝に多発**。軽自動車・コンパクトカーなど車高の低い車ほど危険（[コムテック創研](https://cmken.com/2026/07/the-danger-of-flooded-underpasses-and-life-saving-measures/) / [ユピテル](https://www.yupiteru.co.jp/yupista/article/flooding.html)）
- 既存の対策は「浸水センサ設置」止まりで、**エージェント連携は空白**

## 1-4. 評価

**軸① 課題の新規性と解決策の有効性: ★★★★★**
- 「2人に1人が浸水想定区域外で被災」「内水ハザードマップ公表は7%のみ」は、**"多くの人が抱えながら未解決の課題"の教科書的な証拠**。審査基準の文言にそのまま刺さる。
- 実災害の直後というタイムリーさも強い。

**軸② 自律性・エージェントらしさ: ★★★☆☆（設計次第で★5にもなるし★1にもなる）**
- ❌ 地図を表示するだけ → 「自動化ですらない」で沈む
- ✅ 監視→推定→判断→働きかけ→反応がなければエスカレーション、の能動ループにすれば強い
- 🎯 **防災は「エージェントの自律性を制御しなければならない」題材として最適**。「AIが勝手に避難を指示していいのか」「誤報のコストは誰が負うのか」は、第5回のテーマ（野良エージェントのリスク／ガバナンス）と完全に噛み合う。
  - 承認ゲート（自動通知 / 本人確認 / 自治体承認の3段階）
  - 根拠の提示＝可観測性（なぜ危険と判断したか、どのデータを見たか）
  - 不確実性の明示（「安全」と断言しない設計）

**軸③ 実装品質と拡張性: ★★☆☆☆**
- ⚠️ **最大のリスク: 本物の内水氾濫シミュレーション（2次元不定流解析）は8週間ソロでは無理**
- 現実解: DEM から**窪地抽出・流水集積解析（fill-sink / flow accumulation）を前計算**し、降雨強度と下水道能力（50mm/h）を掛けて**相対リスクスコア**を出す。厳密解ではなく「公式マップ空白域の相対危険度推定」と正直に位置づける（むしろ誠実さは加点される）。
- 前計算は Cloud Run jobs / BigQuery で回し、リアルタイム部分は軽くする → 費用対効果の説明もできる

## 1-5. 絞り込み案（この形なら勝てる）

| 案 | 内容 | 評価 |
|---|---|---|
| **1-A: 白地図の危険を埋めるエージェント** | 内水ハザードマップが無い93%の地域向けに、DEM微地形＋降雨ナウキャスト＋市民報告から「公式マップの空白」の危険度を推定 | 軸①最強。核心を突く |
| **1-B: アンダーパス冠水から移動中の人を守る** | 冠水しやすいアンダーパスを事前特定し、雨中はリアルタイム監視。危険時に通行者・自治体へエスカレーション | 対象が明確、デモしやすい、死者が出ている実課題 |
| **1-C: 行動指南型エージェント** | 自宅の階数・構造（PLATEAU属性）、家族構成、車の有無から「今、垂直避難か水平避難か」「何時までに何をするか」を時間軸で提示 | 研究で必要性が指摘されているが未実装。軸①②とも良い |

**推奨: 1-A ＋ 1-C の合体。** 「公式ハザードマップの空白を埋め、かつ個人の状況に応じて"いつ・何をするか"に変換する」。

**デモの必殺技**: 令和8年8月千葉豪雨を**リプレイ**し、「このエージェントがあれば、あの夜、この人に何時に何を伝えられたか」を時系列で見せる。実災害の再現デモは審査員の記憶に残る。

## 1-6. リスク

- ⚠️ **防災はハッカソンの定番テーマ**。差別化（＝内水・空白域・行動変換）を最初の30秒で言い切らないと埋没する。
- ⚠️ 人命に関わる。「安全です」と誤って言わない設計が必須。逆にそれを設計に織り込めば軸②で加点。
- ⚠️ データ取得が重い。**最初の2週間で「必要なデータが実際に取れるか」を検証するGo/No-Goゲートを置くこと。**
- ⚠️ Google Maps Platform はクーポン対象外 → MapLibre + 地理院タイルで実装する。

# 案2: ハードウェア（ESP32等）× Agentic

## 2-1. 調査で分かった研究動向

### 中核論文: [Skilled AI Agents for Embedded and IoT Systems Development](https://arxiv.org/html/2603.19583)（2026）
- **問題提起**: ①組込みエコシステムの断片化（MCU・フレームワークごとに仕様がバラバラ）②**「コンパイル成功 ≠ 実行成功」**（タイミング制約やハード固有挙動で実機では失敗する）
- **IoT-SkillsBench**: 3プラットフォーム（ATmega2560+Arduino / **ESP32-S3+ESP-IDF** / nRF52840+Zephyr）、23種のペリフェラル、42タスク×3難易度、**実機検証を含む378回のテスト**
- **結果（pass@1）**:

| 条件 | Arduino | ESP-IDF | Zephyr |
|---|---|---|---|
| スキルなし | 88% | 74% | 67% |
| **LLM生成スキル** | 93% | **64%（悪化）** | **45%（悪化）** |
| 専門家作成スキル | 100% | **98%** | 93% |

- **最重要の知見**: LLM が自分で作った"スキル"は**プラットフォーム固有の誤った仮定を強化して性能を下げる**。実ハードの挙動に基づく知識の統合が本質。
- 限界: 電圧不整合（3.3V RTCモジュール）などファームウェアでは解決不能な物理制約、周辺機器仕様の非標準性、人手による実機検証100時間

## 2-2. 評価

**軸① 課題の新規性: ★★★☆☆（ドメイン選び次第で★5にも★1にもなる）**
- 「ESP32を使うこと」自体は課題ではない。**何の課題を解くか**が全て。
- ただし過去受賞作の傾向（3D解剖、Minecraft建築、AR、LEGO物理検証）を見ると、**物理・空間に作用する作品が明確に強い**。→ ハードは傾向に合致。

**軸② 自律性・エージェントらしさ: ★★★★★（3案中で最強）**
- 物理世界に作用するエージェント＝**暴走すれば物が壊れる／人が危険**。
- したがって **承認ゲート・可観測性・非常停止・権限最小化が"作り込むべき必然"になる**。第5回のテーマ「自律性 × ガバナンス」に最も自然に接続する唯一の案。
- 実務パターンとして**リスクに応じた3段階の承認ゲート**（自動実行／通知後実行／人間承認必須）が2026年の定石。「全アクションに承認を求めるマイクロ承認の罠」（人間がボトルネックになりエージェントの価値を殺す）を避ける設計を語れると強い。
- [Model Armor](https://cloud.google.com/security/products/model-armor) でデバイス由来入力（センサ値に混じる文字列、QR、音声）へのプロンプトインジェクションを防御。フィルタ v3 で注入・脱獄検知が強化され、**Gemini Enterprise Agent Platform / Agent Gateway に統合**されている。
- [ADK](https://adk.dev/) は Cloud Trace 連携の**組み込みトレーシング**と**evalset ＋ LLM-as-judge の評価フレームワーク**を持つ → 可観測性・評価をそのまま実装できる。

**軸③ 実装品質と拡張性: ★★★☆☆**
- ⚠️ ハード開発は時間を食う（配線・電源・無線の不安定・部品調達）。上記論文の通り**「コンパイル成功≠実行成功」**は現実の壁。
- ⚠️ **提出要件に「デプロイURL」がある**。ハードだけでは審査員が触れない。
- ✅ **対策**: デバイス実機は**デモ動画**で見せ、**Web の管制ダッシュボードをデプロイURL**にする。ダッシュボード上に**バーチャルデバイス（シミュレータ）**を置き、審査員がテストアカウントでイベントを注入して挙動を確認できるようにする。→ 提出要件を満たしつつ審査しやすくなる。

| **H4** | **独居高齢者の見守り × 物理エージェント** | センサ＋Gemini Live API 音声対話、異常時に段階的エスカレーション。第3回最優秀「フクシア」（社会福祉士支援）と同系統の社会課題路線 | ★★★☆ 既存製品多い | ★★★★☆ | ★★★★☆ |

- **H3 は技術審査員（ゆめみCTO 渡部氏など）に最も刺さる**が、「多くの人が抱える課題」という審査文言に対しては対象が狭い（組込み開発者のみ）。

# 案3: 特定職種へのインタビュー マッチングアプリ

## 3-1. 競合調査

## 3-2. 評価（厳しめ）

**軸① 課題の新規性: ★☆☆☆☆**
- 「特定職種の人に話を聞きたい」は**既に大規模に解決されている課題**。審査基準の「いまだ解決策が与えられていない課題」に真っ向から反する。
- 個人が使いにくい／高い、という不満はあるが、それは**価格と規模の問題**でハッカソンの8週間で覆せない。

**軸② 自律性・エージェントらしさ: ★☆☆☆☆（致命的）**
- マッチングアプリの本質は **CRUD ＋ 検索 ＋ メッセージング**。エージェント要素を後付けしても「単純な自動化」と評価されやすい。
- 第5回で最も重視される「状況判断して自律的に行動する」「可観測性・セキュリティ」を語る余地が薄い。

**軸③ 実装品質と拡張性: ★★☆☆☆**
- 🔴 **two-sided marketplace の cold start 問題が審査で直撃する。** 審査員はテストアカウントとサンプルデータで審査するが、マッチングアプリは登録者がいなければ「空の箱」。サンプルデータを大量に仕込むと、提出要件の「**主要機能がモックではなく実際に実装されていることが分かる**」に対して不利に働く。
- 実装自体は簡単なので、逆に「技術的挑戦がない」と見られる。

**→ 3案の中で明確に最下位。このままの形では推奨しない。**

## 3-3. 救済路線（もしこの領域をやるなら）

「マッチング」を捨て、**「インタビューそのものをエージェントが遂行する」**に転換すれば軸②が立つ。

> **AIリサーチャー**: 調査目的を与えると、①仮説と質問設計を自律生成 → ②候補者を探索・打診 → ③**Gemini Live API で実際に音声インタビューを実施** → ④回答をその場で分析して**次の質問を動的に組み替える** → ⑤複数人の結果を統合して示唆と反証を出す → ⑥「聞けていない論点」を自分で見つけて追加インタビューを設計

- two-sided である必要がなくなる（片側だけで動く）＝ cold start 回避
- 「状況を判断して次の行動を選ぶ」が本質機能になる ＝ 軸②が立つ
- 誘導尋問・個人情報・録音同意 → セキュリティ／ガバナンスの題材にもなる
- ⚠️ ただし「AIが面接・インタビューする」プロダクトは既に多数存在するため、軸①の新規性は中程度にとどまる

# ◎ 推奨案: 案1 × 案2 の合体

> ## 「アンダーパス／内水氾濫 — 見えない浸水を、現場のセンサと自律エージェントで塞ぐ」

**なぜ強いか**

| 審査軸 | 効き方 |
|---|---|
| ① 課題の新規性と解決策の有効性 | 千葉豪雨で**実際に死者が出た**（冠水アンダーパスから遺体）。過去20年で全国20人以上が車両水没で死亡。かつ**内水ハザードマップは7%しか整備されていない＝公式には危険が"存在しないこと"になっている**。「多くの人が抱えながら未解決」の証拠が数字で揃っている |
| ② 自律性・エージェントらしさ | **「AIが道路を封鎖してよいのか」＝ HITL の完璧な題材**。危険度別3段階ゲート（①注意喚起は自動 ②通行者への警告は通知後実行 ③通行止め相当の判断は人間承認必須）。センサ値の欠測・故障・なりすまし＝可観測性とセキュリティの必然。「野良エージェント」テーマと直結 |
| ③ 実装品質と拡張性 | センサ1台＝数千円で、全国のアンダーパスに横展開できるコスト構造を語れる（費用対効果）。クラウド側は Cloud Run（min-instances=0）で待機コストゼロ |
| デモ映え | **実機のセンサをバケツの水に沈めると、クラウドのエージェントが判断してダッシュボードが赤く光り、警告が飛ぶ** —— 3分の動画で最も強い絵 |

**構成イメージ**
- **デバイス**: ESP32-S3 ＋ 水位センサ（フロート／超音波／静電容量）＋ カメラ（任意）→ MQTT/HTTPS で送信
- **クラウド**: Cloud Run 上に ADK エージェント。DEM微地形解析で「冠水しやすいアンダーパス」を全国から事前抽出（センサが無い場所も推定でカバー）＋ 降雨ナウキャスト ＋ 実センサ値を統合して判断
- **ガバナンス**: Model Armor で外部入力を検査／Cloud Trace で判断根拠を全トレース／3段階承認ゲート／デバイス側ハード非常停止
- **提出要件**: 管制ダッシュボードをデプロイURLに。**バーチャルデバイス機能**を付け、審査員がテストアカウントで水位イベントを注入して挙動を確認できるようにする（実機が無くても審査可能）
- **デモ動画**: ①千葉豪雨の実データでリプレイ ②実機バケツ実験 ③承認ゲートの発動シーン

**8週間の進め方（Go/No-Goゲート付き）**
| 週 | やること | ゲート |
|---|---|---|
| W1（〜8/26） | データ検証: 地理院DEMタイルから標高が取れるか／アンダーパス位置データの所在／気象庁JSONの安定性。ESP32と水位センサの部品調達 | **データが取れなければ案を差し替える** |
| W2 | DEM微地形解析の前計算パイプライン（Cloud Run jobs）。ESP32からクラウドへ疎通 | 疎通できなければ通信方式を変更 |
| W3–4 | ADKエージェント本体（監視→判断→行動）＋ダッシュボード ＋ Cloud Run デプロイ | |
| W5 | ガバナンス層（3段階ゲート／Model Armor／Cloud Trace／評価セット） | |
| W6 | バーチャルデバイス、テストアカウント＋サンプルデータ、千葉豪雨リプレイ機能 | |
| W7 | 実機バケツ実験の撮影、デモ動画編集、アーキ図 | |
| W8（〜10/14） | Zenn記事、タグ打ち、提出 | |

**この案の弱点（正直に）**
- ハード調達・実装で1〜2週間持っていかれる。W1でハードが動かなければ**センサ部分を切り離し、案1-A（DEM＋降雨のみの推定エージェント）に縮退する退避プランを用意しておくこと。**
- 防災は定番テーマ。「内水」「公式マップの空白」「アンダーパス」という3つの絞り込みを冒頭で言い切ること。
