# 採点ルーブリック（第 5 回 Agentic AI Hackathon with Google Cloud の審査基準から作成、10/2）

> 出典: 規約第 7 条の審査基準 3 軸（`context/03-rules-requirements.md` の「審査基準」、`.claude/skills/gc-hackathon-vol5/references/regulations.md`）と提出物の要件。
> 3 軸を観点に分け、各観点を 1〜5 点で採点する。軸ごとの点は観点の平均 × 20（100 点満点）、総合は 3 軸の平均。
> 審査員は 1 次審査から全提出物を精査するとは限らない。**説明文の冒頭・アーキテクチャ図・デモ動画の最初の数十秒**で伝わるかも、各観点で見る。

## 点の目安（全観点共通）

| 点 | 意味 |
|---|---|
| 5 | 入賞作の水準。審査員がそのまま褒める言葉を書ける。証拠（コード・画面・数字）がそろい、弱点も正直に書かれている |
| 4 | 強い。小さな穴が 1〜2 個あるが、主張は証拠で支えられている |
| 3 | 平均的な提出作。主張はあるが、証拠が薄いか、よくある作りにとどまる |
| 2 | 弱い。主張と実装がずれている、またはモック・未実装が目立つ |
| 1 | 欠けている。審査員がこの観点で評価できない |

## 軸 1. 課題の新規性と解決策の有効性

> 多くの人が抱えながらも、いまだ解決策が与えられていない課題を発見できているか。提案されたソリューションがその課題の核心に効果的に対処し、実質的な価値をもたらしているか。

| # | 観点 | 5 点の姿 |
|---|---|---|
| 1-1 | 課題の実在と規模 | 誰が・どれだけ困っているかが一次資料の数字で示され、出典が確かめられる |
| 1-2 | 未解決であること | 既存ツール（ロイロ・Classroom・専用センサーなど）で足りない理由が具体的 |
| 1-3 | 解決策が課題の核心を突く | 「器具がない」「予想と証拠の往復ができない」「先生が一人」に直接効く。使う場面（50 分の授業のどこか）が具体的 |
| 1-4 | 実質的な価値と導入しやすさ | 費用・端末・学校の制約（BYOD 禁止、iPad・Chromebook）を踏まえ、明日の授業で使える |
| 1-5 | 伝わり方 | 説明文の冒頭 3 行と動画の最初の 15 秒で、課題と解決が伝わる |

## 軸 2. 自律性・エージェントらしさ

> 単純な自動化を超え、状況を判断しながら自律的に行動するエージェントとして設計されているか。その自律性が適切に管理・制御されており、可観測性やセキュリティへの配慮を持った、信頼できる動作をするか。

| # | 観点 | 5 点の姿 |
|---|---|---|
| 2-1 | 状況判断と自律的な行動 | エージェントが入力（予想・検査の結果・学級の様子）を読み、状況に応じて違う行動を選ぶ。ループ（計画 → 実行 → 結果を見て次を決める）が閉じている |
| 2-2 | 単純な自動化を超えているか | 決まった手順の呼び出しではなく、判断が要るところに LLM を置き、要らないところ（測定・判定）は機械にしている。その線引きに理由がある |
| 2-3 | ツール使用・複数エージェント | エージェントがツールで情報を取りに行く、役割の違う複数のエージェントが協調する。必要性が説明されている |
| 2-4 | 管理・制御（人間の関与・上限・停止） | 承認・上限・停止が実装されていて、人が最終決定者。エージェントが勝手に操作しない |
| 2-5 | 可観測性 | 判断の跡が利用者・先生・開発者のそれぞれに見える（画面、トレース）。本文などの個人情報はトレースに入れない |
| 2-6 | セキュリティ | 注入・禁止動作・答えの漏えい・他人の記録の改ざん・総当たりへの備えが、多層で実装され、評価の数字がある |
| 2-7 | 信頼できる動作 | 失敗時（LLM が遅い・落ちる・おかしな出力）に安全側に倒れる。自己修正や縮退があり、テストで確かめられている |

## 軸 3. 実装品質と拡張性

> アイデアをどれだけ高い品質で実現できているか。必要なツールを適切に活用し、拡張性・運用性・費用対効果を考慮した、実用に耐えるソリューションを構築できているか。

| # | 観点 | 5 点の姿 |
|---|---|---|
| 3-1 | 動くこと（モックでないこと） | 主要機能が本番 URL で動き、テストアカウントとサンプルデータで審査員が試せる。実装済みと未実装の線引きが正直 |
| 3-2 | コードの品質 | 責務が分かれ、読みやすく、型とテストがある。エラー処理が明示的 |
| 3-3 | テストと評価 | 単体・API のテストに加え、本物のモデルでの評価（数字）がある |
| 3-4 | Google Cloud の適切な活用 | Cloud Run・Vertex AI・ADK・Firestore・Cloud Trace・Model Armor などを、必要な理由とともに使っている |
| 3-5 | 拡張性 | 実験・テーマ・学校種・エージェントを足すときの道筋がコードと文書に見える |
| 3-6 | 運用性 | デプロイ手順、設定（env）、監視・トレース、レート制限、審査期間中の維持が考えられている |
| 3-7 | 費用対効果 | 1 実験・1 学級あたりの費用が数字で出ていて、アイドル課金がない |
| 3-8 | 実機・現場での有効性 | 実機（iOS / Android / iPad）での測定精度が確かめられ、閾値に根拠がある |

## 提出物の完成度（点数には入れないが、欠けると失格・減点になるもの）

- [ ] GitHub リポジトリ（ダッシュボードの GitHub App 連携）、デフォルトブランチ
- [ ] デプロイ URL、テストアカウント（ソーシャルログイン・メール受信なし）、サンプルデータ
- [ ] 説明文（ユーザー像・課題・ソリューション・特徴）
- [ ] アーキテクチャ図の画像（実装と一致しているか）
- [ ] 3 分のデモ動画（YouTube 公開）
- [ ] OSS ライセンスの明記、開発した部分の構成説明

## 採点の出力の形（採点者への指示）

1. 観点ごとに「点（1〜5）・根拠（ファイルパス:行、または文書の箇所）・5 点に届かない理由」を表で
2. 軸ごとの点（100 点満点）と総合
3. **点が最も上がる改善 10 個**（観点・何をするか・上がる見込みの点・手間（小 / 中 / 大）・締切 10/13 までにやるべきか）。手間あたりの上がり幅が大きい順
4. 審査員が最初の 1 分で抱きそうな疑問・突っ込み 5 つと、その答えがリポジトリのどこにあるか（無ければ「無い」）
5. 提出物の完成度のチェックで、欠けているもの
