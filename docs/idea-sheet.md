## 課題とユーザー

- **対象ユーザー**: 中学校で理科を学ぶ生徒と、実験を担当する理科教員。まず中 3「力学的エネルギー」（振り子）と中 1「音の高さ」。授業の端末は学校の GIGA 端末（Chromebook・iPad）。高校（物理基礎、共通テストの実験・グラフ問題）は後から足す。
- **解決する課題・実現したい価値**:
  - 理科の実験が減っている。小中高の理科で「最も困っていること」は 12 年連続で観察・実験機器の不足。理科教員の 66% が準備・片付けの時間不足で、週 1 回以上実験する教員は 55%。
  - 実験しても「結果から関係を見いだす」力が育っていない。物理基礎で実験結果から関係を見いだす問題の通過率は 38.4%。
  - 一方で GIGA スクール構想で中学生には 1 人 1 台の端末があり、最低スペック基準で前後カメラとマイクは全台に付いている（加速度・ジャイロは iPad など一部）。教育用の無線加速度センサーは 1 台 $99〜119 で、8 班ぶんで約 15 万円。
  - 学習指導要領の解説も「各種のセンサを用いた計測」「動画のコマ送り」「コンピュータで音を波形表示」を例に挙げている。中学の教科書の観察・実験 82 件のうち、光・音・力・運動の 12 件中 7 件を端末で扱え、扱える 13 件のうち 10 件はカメラとマイクだけで動く（`docs/curriculum-coverage.md`）。
  - PhoneLab は **器具を買わずに、生徒の「思い込み」を手元の端末の測定で壊す** 体験を届ける。AI は答えを言わず、予想を区別できる実験を選ぶだけ。判断と解釈はいつも生徒。
- **現状の代替手段とその不満・物足りなさ**:
  - phyphox などのスマホ測定アプリ: 測定器としては優秀だが、「何を測れば自分の予想を確かめられるか」は生徒任せ。怪しいデータも止めない。
  - ストップウォッチ: 自由落下の 0.45 秒や音の高さはそもそも測れない。
  - 生成 AI に聞く: 答えが先に出て、実験が「答え合わせ」になる。AI が書いたレポートと測った記録の区別がつかない。

## ソリューション

- **概要（3 行以内）**:
  端末が実験器具。生徒が「重い振り子ほど、いちばん下で速くなる」と予想を書くと、Agent がその予想を壊せる最小の実験をカタログから選び、生徒が「加速度・ジャイロを 10 秒」を承認して測る。二つのセンサーの一致を機械が検査し、怪しければ結論を保留。通った測定だけに署名して一本の実験記録にする。
- **エージェントが自律的に行うこと（観察→判断→行動の流れ）**:
  1. **観察**: 生徒の予想（自由記述）を読み、変数と向き（重さ / 速くなる）を解釈する。予想に理由が無ければ実験を出さず問い返す（予想ゲート）
  2. **判断**: 端末の能力と学級の許可で絞った実験カタログから、その予想を区別できる最小の実験を選ぶ（何を変え、何を一定にし、どのセンサーを何秒）
  3. **行動**: 許可チップとして提示し、生徒の承認後にだけセンサーを読む。測定の特徴量を機械が検査し、欠測・飽和・二系統不一致なら保留して再測定の条件を提案。通れば判定文を生成し、未知の条件での「次の予測」を求めて次の実験へ
  4. **軌道修正**: 同じ端末で二系統不一致が続けば検査方式を切り替える。カタログ外・危険な要望は却下して最も近い代替を提示。学級許可で不可ならさらに次の代替へ
  5. **学級の観察（二層目の Agent）**: 教員側の ClassAgent が 31 人の予想の分布・保留・却下を観察し、「重さで速くなると思っている生徒が 6 割」「S-11 は飽和が 3 回続く」と要約して、次に学級で試す実験や注意すべき生徒を **提案** する。提案は教師が承認して初めて学級の設定に反映される。全端末停止は提案の種類に存在しない（止めるのは人だけ）
- **ガバナンス・セキュリティの考慮（エージェントの行動制御・監査など）**:
  - **権限分離**: LLM（Gemini）は Planner だけ。Policy（安全・センサー最小集合・秒数上限）と Verifier（欠測・飽和・二系統一致）は決定論で LLM は読まない
  - **Human-in-the-loop**: 許可は実験単位・秒数付き。承認ボタンの真上に「何を、何秒」。位置情報は永久に要求しない
  - **データ最小化**: 生データ（波形・音声・映像）は端末から出ない。送るのは周期・周波数などの特徴量とそのハッシュ
  - **プロンプトインジェクション対策**: 三層。① Model Armor で生徒入力を検査（日本語検出のため us-central1 のテンプレート）② 決定論のパターン検査 ③ Planner の出力は構造化 JSON でカタログ内の実験しか選べない。「安全チェックを飛ばせ」は禁止動作名・無視した文・代替実験をセットで却下
  - **統制は ADK のコールバックそのもの**: Policy は Runner に登録した Plugin。`on_user_message`（Model Armor）→ `before_model`（上限・停止）→ `after_model`（漏えい検知・Policy 検査）→ `before_tool`（ClassAgent の提案制限）。二つの Agent に同じ統制が一箇所でかかる
  - **答えの漏えい防止**: Planner にカタログの「答え」を渡さない。出力を漏えい検知にかけ、漏らしたら失敗として数える。ヒントは 3 回 / 実験
  - **停止と上限**: 生徒「測定をやめる」、教師「全端末を止める」が一タップ。Planner 呼び出し・再測定・トークンに上限
  - **可観測性**: 1 実験 = 1 トレース（ADK → Cloud Trace）。教員画面で生徒ごとのトレースを日本語で読める。許可・計画・承認・測定・検査・保留の理由・却下の理由・署名が一本の記録に残る
  - **署名**: 検査を通った記録だけ Cloud KMS で署名。AI で書いたレポートと測った記録の区別がつく

## 実現構成

- **実行プロダクト**: **Cloud Run**（API + ADK エージェント + PWA 配信。min-instances=0 でアイドル課金ゼロ）
- **AI 技術**: **Gemini API（Gemini Enterprise Agent Platform 経由）+ Agent Development Kit（ADK）**。加えて Model Armor（入力検査）
- **アーキテクチャ案**:
  - 生徒の端末（PWA。GIGA 端末と私物スマホ）: DeviceMotion / getUserMedia / Web Audio で測り、速さ・振動数などを端末内で計算。センサーは実行時に調べ、カメラ・マイクだけの端末にはそれで測れるテーマを出す。生データは端末内。通信が切れたら固定手順に縮退して測定だけ続ける
  - Cloud Run: FastAPI + ADK Runner。StudentAgent（Planner。Gemini、structured output、ツールなし）と ClassAgent（教員側の観察。ツール 3 つ）。統制は `PolicyPlugin` のコールバック。Verifier（決定論）→ Judge（テンプレート）→ Sign（Cloud KMS）は ADK の外の純関数
  - Model Armor: 生徒の自由記述を Planner の前で検査（テンプレートは us-central1。東京リージョンは多言語検出が無いため）
  - Firestore: 学級ポリシー、生徒番号、実験記録。実験カタログ JSON と答えは分離（答えはサーバのみ）
  - Cloud Trace / Cloud Logging: ADK の組み込みトレース＋自前スパン。教員画面の指標はログベース
  - 教員画面（Web）: 学級の許可トグル、ヒント・秒数の上限、全端末停止、トレース閲覧
  - 図: `flow.md` 1.3 章の mermaid（提出用 PNG は F1 で作る）

## スコープ

- **ハッカソンで作るもの（MVP）**:
  - 実験: 中 3「振り子と力学的エネルギー」（放す高さ / 重さ → いちばん下での速さ。ジャイロと加速度の二系統）、中 1「音の高さ」（はじく強さ / 震える長さ → 振動数。マイクだけで Chromebook でも動く。基本周波数と倍音の二系統）
  - 生徒の 6 画面: 予想と承認 / 測定と検査 / 結果と次の予測 / 保留 / Policy 却下 / 署名付き実験記録
  - 教員画面: 許可・上限・全端末停止・トレース・ClassAgent の提案の承認
  - 統制層: Policy（ADK Plugin）、Model Armor、Verifier、Trace、署名、上限、漏えい検知
  - ClassAgent: 学級の観察と提案（W4。時間が無ければ「要約だけ」に縮退）
  - テスト学級 `DEMO-2026` とサンプル記録
- **時間が余ったら足すもの**: 高校の入口（物理基礎の実験、振り子の周期、共通テスト形式のグラフ読み取り）、振り子を机の上から撮る動画版、自由落下（カメラ＋マイク）、ペットボトルの音、記録の PDF 書き出し、Zenn 記事
- **作らないと決めたもの**: ネイティブアプリ、ソーシャルログイン、氏名の保持、位置情報、生データのアップロード、スマホを落とす・投げる実験、phyphox 級の汎用測定機能、教師向けの成績管理

## リスク・次に検討すること

- iOS Safari の DeviceMotion 許可（ユーザー操作内でのみ）とサンプリングレートの機種差 → スパイク B（9/14 まで）で Go/No-Go。No-Go なら音の高さ（マイク）を主役に
- Model Armor のリージョン・権限 → 使えなければ決定論フィルタで代替し README に明記
- 加速度とジャイロの速さの一致（0.15 m/s）と、基本周波数と倍音の一致（3%）が実機で収まるか → 収まらない機種は「保留」で見せる（設計どおり。閾値は B7 で決め直す）
- 出典台帳（`idea/2026-09-09-phonelab-why-phone-and-ux.md`）が手元に無い。説明文の数字（12 年連続、97.1%、38.4%、$99〜119、1〜3%）に URL を付け直す
- 中学は私物スマホを授業で使えない（2020 年の文科省通知で原則持込み禁止）→ 最初から GIGA 端末を前提にする。Chromebook（GIGA の 6 割）は加速度が無い機種があるので、カメラ・マイクだけで動くテーマ（音の高さ）を必ず用意し、加速度の実験は iPad の学校と家庭学習へ
