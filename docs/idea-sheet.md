## 課題とユーザー

- **対象ユーザー**: 中学校で理科を学ぶ生徒と、実験を担当する理科教員（`docs/personas.md`）。一人目は ゆい（中 1、学校所有の iPad、「音の高さ」）。先生は佐藤先生（12 年目、4 クラス、実験助手なし。観察実験アシスタントがいるのは小中学校の約 9%）。授業は学校の端末、家の続きは私物のスマホ（先生が有効化した実験だけ）。高校（物理基礎、BYOD が当たり前）は後から足す。
- **使う場面**: 教室が主、家が従。50 分のうち「予想 → 判定」の 20 分を PhoneLab が引き受け、考察・共有・まとめは先生と既存ツールに返す。記録は 1 人 1 台、測定は班で順番。
- **解決する課題・実現したい価値**:
  - 理科の観察・実験を週 1 回以上行う中学校は 48.5%（令和 7 年度 全国学力・学習状況調査の学校質問）。文科省の観察実験アシスタント配置事業の資料では、令和 3 年度の配置校は 2,649 校（同年度の小中学校は 29,563 校。自治体独自の配置は含まないので、全国の配置率ではない）で、多くの理科教員は準備から片付けまで一人で担うと考えられる（中学校理科教員の 66% が準備・片付けの時間不足と回答。平成 24 年度の JST 調査なので参考値）。出典は `docs/personas.md` §5。
  - 一方で GIGA スクール構想で中学生には 1 人 1 台の端末があり、最低スペック基準で前後カメラとマイクは全台に付いている（加速度・ジャイロは iPad など一部）。教育用の無線加速度センサーは 1 台 $99〜119 で、8 班ぶんで約 15 万円。
  - 学習指導要領の解説も「各種のセンサを用いた計測」「動画のコマ送り」「コンピュータで音を波形表示」を例に挙げている。中学の教科書の観察・実験 82 件のうち、光・音・力・運動の 12 件中 7 件を端末で扱え、扱える 13 件のうち 10 件はカメラとマイクだけで動く（`docs/curriculum-coverage.md`）。
  - PhoneLab は **専用の測定器具を買わずに（輪ゴム・箱・糸など身近な材料は使う）、生徒の「思い込み」を手元の端末の測定で確かめる** 体験を届ける。AI は答えを言わず、予想を区別できる実験を選ぶだけ。判断と解釈はいつも生徒。
- **現状の代替手段とその不満・物足りなさ**:
  - phyphox などのスマホ測定アプリ: 測定器としては優秀だが、「何を測れば自分の予想を確かめられるか」は生徒任せ。怪しいデータも止めない。
  - ストップウォッチ: 自由落下の 0.45 秒や音の高さはそもそも測れない。
  - 生成 AI に聞く: 答えが先に出て、実験が「答え合わせ」になる。AI が書いたレポートと測った記録の区別がつかない。

- **既存ツールとの違い（差別化）**: **ロイロは予想を集める。PhoneLab は予想を壊す。** ロイロノート・Google Classroom・MetaMoJi ClassRoom はどれも「端末のセンサーで測る」「AI が実験を選ぶ」「機械が検査して保留する」を持たない。重なるのは予想の提出・共有と記録だけなので、そこで戦わず隣に置く（併用前提）。宿題の配布・締切・メッセージは持たない。比較表は `docs/personas.md` §4。

## ソリューション

- **概要（3 行以内）**:
  端末が実験器具。生徒が「強くはじくと音が高くなる」と予想を書くと、ラボ先生（Gemini）がその予想を確かめられる実験をカタログから選び、生徒が「マイクを 5 秒」を承認して測る。二本の時計の一致を機械が検査し、怪しければ結論を保留する。結果を読んだラボ先生は、次に何を確かめるかを自分で選び、次の予想を促す。答えは言わない。
- **エージェントが自律的に行うこと（観察→判断→行動の流れ）**:
  1. **観察**: 生徒の予想（自由記述）を読み、変数と向き（はじく強さ / 高くなる）を解釈する。「なぜ」の理由が無ければ実験を出さず 1 回だけ問い返す（予想ゲート）
  2. **判断**: 学級の許可とやり終えた実験で絞った候補から、その予想を確かめられる実験を選ぶ（評価: 25 件中 25 件で予想の変数を変える実験を選んだ。端末のキーワード規則は 23 件で、「消しゴムを足す（＝重さ）」や英語の予想を外す）
  3. **行動**: 許可チップとして提示し、生徒の承認後にだけセンサーを読む。特徴量を機械が検査し、欠測・飽和・二系統不一致、または差が測定のばらつきに埋もれたら保留する
  4. **軌道修正**: 保留になったら、ラボ先生が保留の理由を読み、同じ実験で直して測り直すか別の実験へ切り替えるかを提案する。結果が出たら、予想と測定が合ったか・生徒が理由を書いたかを読み、次の実験（または先にふり返り）を選ぶ。理由を書いた・測り直した、で読み直す
  5. **自己修正**: 統制層の検査に落ちた出力（候補外の実験、結果の言葉）は、理由を添えて 1 回だけ作り直させる。それでも落ちたら統制層が差し替える
  6. **学級の見立て（二つ目の視点）**: 先生が押すと、ラボ先生が読み取り専用のツール 2 つで学級の要約を読み、「音の高さで 3 人がまわりの雑音で保留、周囲の班の音が共通の原因の可能性」のように 3 行と見に行く順を返す。**操作はしない**（止める・許可を変えるのは先生のボタンだけ）
- **ガバナンス・セキュリティの考慮（エージェントの行動制御・監査など）**:
  - **権限分離**: LLM（Gemini）が受け持つのは、予想の読み取りと実験の選択、保留と結果のあとの次の一手、学級の見立て、ふり返りの会話。安全の判定・測定の検査・判定文・停止は決定論で、LLM は関与しない
  - **Human-in-the-loop**: 許可は実験単位・秒数付き。承認ボタンの真上に「何を、何秒」。位置情報は永久に要求しない
  - **データ最小化**: 生データ（波形・音声）は端末から出ない。送るのは周波数・速さなどの特徴量の要約。エージェントに予想の本文と名前は渡さない（学級の見立て）
  - **プロンプトインジェクション対策**: 三層。① Model Armor（us-central1）で生徒の文を検査 ② 決定論のパターン検査 ③ 構造化出力と出力の検査（候補外の実験・生徒が書いていない結果の言葉・説明の漏えい・実験の条件を変えさせる助言）。評価では注入・禁止動作 20 件のうち 10 件がモデルまで届き、最終出力に答えや結果が出たのは 0 件。別のモデル（gemini-3.8-flash）に答えを見せて判定させても、全出力 78 件で漏えい 0 件。Model Armor は日本語の言い換えの多くを拾わなかったので、三層で守る
  - **統制は ADK のコールバックそのもの**: `PolicyPlugin` を App に登録し、5 つのエージェントに同じ統制がかかる。`before_run`（停止）・`before_model`（Model Armor・回数上限）・`before_tool`（許可したツール・回数・番号）・`after_model`（出力の検査）
  - **停止と上限**: 生徒「測定をやめる」、教師「全端末の測定を止める」が一タップ。測定中の端末は 2 秒ごとに学級の状態を確かめて止まり、停止中はサーバがエージェントを動かさない（409）。エージェントを呼ぶ回数は、学級の生徒ならサーバが数える
  - **可観測性**: エージェントの判断は「判断の跡」（何を読み、何を選び、統制層が何を直したか）として生徒の画面・教員画面の記録・Cloud Trace に同じ段で残る。生徒の文はトレースに入れない
  - **記録**: 予想・計画・許可・測定・検査・保留の理由・却下の理由・次の一手が一本の記録に残る。いまの「署名」は端末で計算したハッシュで、Cloud KMS の署名は設計だけ（未実装）

## 実現構成

- **実行プロダクト**: **Cloud Run**（API + ADK エージェント + Web アプリの配信。min-instances=0 でアイドル課金ゼロ）
- **AI 技術**: **Gemini API（Gemini Enterprise Agent Platform 経由）+ Agent Development Kit（ADK）**。加えて Model Armor（入力検査）
- **アーキテクチャ案**:
  - 生徒の端末（Web アプリ。GIGA 端末と私物スマホ）: DeviceMotion / getUserMedia / Web Audio で測り、速さ・振動数などを端末内で計算。センサーは実行時に調べ、カメラ・マイクだけの端末にはそれで測れるテーマを出す。生データは端末内。通信が切れたら固定手順に縮退して測定だけ続ける
  - Cloud Run: FastAPI + ADK。エージェントは Planner・Replanner・NextStep・ClassAgent（読み取り専用ツール 2 つ）・Tutor の 5 つ（Gemini 3.5 Flash-Lite、構造化出力）。統制は `PolicyPlugin` のコールバック。測定の検査と判定は端末の決定論（サーバ側の再検証は設計だけ）
  - Model Armor: 生徒の自由記述を Planner の前で検査（テンプレートは us-central1。東京リージョンは多言語検出が無いため）
  - Firestore: 学級ポリシー、生徒番号、実験記録。実験カタログ JSON と答えは分離（答えはサーバのみ）
  - Cloud Trace: ADK の組み込みトレース＋自前スパン（`phonelab.policy`・`phonelab.model_armor`・`phonelab.self_correct`）
  - 教員画面（Web）: 予想の分布・見に行く子・ラボ先生の見立て・記録の流れ（判断の跡と Cloud Trace へのリンク）・許可トグル・全端末停止
  - 図: `docs/architecture.png`

## スコープ

- **ハッカソンで作るもの（MVP）**:
  - 実験: 中 3「振り子と力学的エネルギー」（放す高さ / 重さ → いちばん下での速さ。ジャイロと加速度の二系統）、中 1「音の高さ」（はじく強さ / 震える長さ → 振動数。マイクだけで Chromebook でも動く。基本周波数と倍音の二系統）
  - 生徒の画面: 予想と承認 / 測定と検査 / 結果と次の一手 / 保留 / Policy 却下 / 実験記録（端末のハッシュ）
  - 教員画面: 分布・見に行く子・学級の見立て・記録の流れ・許可・全端末停止
  - 統制層: PolicyPlugin（4 コールバック）、Model Armor、自己修正、判断の跡、上限、漏えい検知
  - テスト学級 `DEMO-2026` と見本の記録 D-01〜D-06
  - 作らなかったもの: Cloud KMS の署名、サーバ側の再検証、見立ての提案を承認して学級の設定に反映する UI
- **時間が余ったら足すもの**: 高校の入口（物理基礎の実験、振り子の周期、共通テスト形式のグラフ読み取り）、振り子を机の上から撮る動画版、自由落下（カメラ＋マイク）、ペットボトルの音、記録の PDF 書き出し、Zenn 記事
- **作らないと決めたもの**: ネイティブアプリ、ソーシャルログイン、氏名の保持、位置情報、生データのアップロード、スマホを落とす・投げる実験、phyphox 級の汎用測定機能、教師向けの成績管理

## リスク・次に検討すること

- iOS Safari の DeviceMotion 許可（ユーザー操作内でのみ）とサンプリングレートの機種差 → スパイク B（9/14 まで）で Go/No-Go。No-Go なら音の高さ（マイク）を主役に
- Model Armor のリージョン・権限 → 使えなければ決定論フィルタで代替し README に明記
- 加速度とジャイロの速さの一致（0.15 m/s）と、基本周波数と倍音の一致（3%）が実機で収まるか → 収まらない機種は「保留」で見せる（設計どおり。閾値は B7 で決め直す）
- 出典台帳（`idea/2026-09-09-phonelab-why-phone-and-ux.md`）が手元に無い。説明文の数字（12 年連続、97.1%、38.4%、$99〜119、1〜3%）に URL を付け直す
- 中学は私物スマホを授業で使えない（2020 年の文科省通知で原則持込み禁止）→ 最初から GIGA 端末を前提にする。Chromebook（GIGA の 6 割）は加速度が無い機種があるので、カメラ・マイクだけで動くテーマ（音の高さ）を必ず用意し、加速度の実験は iPad の学校と家庭学習へ
